# PDFI4 Explicit Blank And Applicability Checkpoint

This remains an inactive prerequisite for [PDFI4](pdf-agentic-intake-pdfi4-goal.md), not production enablement or exit.
It depends on the [native output-scope contract](pdf-agentic-intake-pdfi4-output-scope-checkpoint.md). Private draft
interpretation, production composition, real model/channel qualification and output verification remain required.

## One Existing Intake Transaction

The private interpreter may propose `intentionally_blank` or `not_applicable`, supported by one exact operator
instruction fragment. Native validation writes an existing encrypted blank ledger event with a distinct state and
reason; it never turns that instruction into a supplied string or manufactures an `N/A` answer. Source-required fields
still block blank/applicability proposals. Clearing an accepted value needs explicit correction evidence and exact
event supersession; clearing a source value needs explicit correction and replacement authority.

One section instruction may legitimately apply to several fields across eight-field views. Its exact source span is
accounted once as scoped instruction evidence, not as a positive fact or disposable prose. Only an identical scoped
span may be shared; overlapping positive facts and non-data classifications still refuse. The same instruction may
also explicitly prove correction, without duplicating its accounting as prose.

The existing bounded reservation/outcome list proves which writable fields have been considered. An instruction
cannot be discarded after its first window; it remains encrypted until all views are covered and existing findings
and text-accounting gates pass. This adds no cursor, planner, queue, store or per-form production rule. All existing
message, pass, literal, candidate and retention bounds remain unchanged. Accepted events, instruction accounting and
replay outcome still publish together in the existing atomic snapshot write; failed publication returns no acceptance.

## Compatibility And Qualification Boundary

Optional scoped-evidence metadata preserves the exact digest shape of legacy positive-fact proposals. Current readers
accept old snapshots. Older strict readers refuse active intake metadata containing the new optional scoped flags;
retain a disposition-capable reader while those intake records remain. The output-capability metadata has its separate
minimum-reader requirement described in the prerequisite. Disabling composition is not a snapshot downgrade.

Native tests cover section-wide instructions beyond the first eight fields, restart, exact replay, required fields,
source and accepted-value replacement, positive-fact/non-data overlap, owner/schema/revision boundaries and failed
publication. A mocked tool-bridge test uses an ordinary protected message across thirteen fields, with safe public
projections and no second model call on receipt replay. Private wire tests enforce the bounded disposition vocabulary.
These are not proof of actual PDF output, language-model interpretation, Telegram ingress or deployed operation.
